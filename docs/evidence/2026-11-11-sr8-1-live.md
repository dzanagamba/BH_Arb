# 2026-11-11 SR8-1 live feeds: Betole fixed, Mozzartbet is websocket-only

**Question:** in the 2026-11-11 and 2026-11-08 live scans, Mozzartbet and Betole
answered with bytes but parsed to zero matches (`kind: empty`). Does either feed
carry live events, and where does the adapter lose them?

**Method:** the adapters' own requests were replayed as probes (Betole over its
HTTP policy, Mozzartbet through its browser session), and the books' own pages
were opened in plain headless Chromium to label the prices. No login, no stake,
nothing submitted.

## Betole — the feed has live events; the registry had no live rows

The live desk answered with **1,034 events, 76 of them live** (`live: true`,
`blocked: false`), each carrying the same `{pick_code: price}` map as prematch.
`_parse_betole_markets(mode="live")` returned nothing because
`config/bookmaker_markets.json` had `"live": {}` for Betole: every pick code was
recorded unmapped and the adapter deliberately priced nothing (the limitation
recorded in `docs/MULTISPORT_EVIDENCE.md`).

**Label proof.** The adapter reads the full offer (`by-ids`), not the trimmed
desk. For three live fixtures the site's own `/match-special/{event_id}` page
was opened and every displayed label/price was matched against the payload the
page itself loaded (`/restapi/offer/ba/match/{id}`):

| Fixture | Codes proven |
|---|---|
| `91419732` Fuerte San Francisco – Alianza FC | 1/2/3 → 1/X/2 at 3.10/3.20/2.10; 7/8/9 → 1X/12/X2 at 1.60/1.26/1.28; 272/273 → GG/NG at 1.71/1.95; 242/21 → Over/Under 1.5 at 1.23/3.45; 24/22 → O/U 2.5 at 1.83/1.81; 25/219 → O/U 3.5; 27/453 → O/U 4.5; 223/266 → O/U 5.5 |
| `91429406` Independiente Petrolero – Always Ready | same code map, every price matched |
| `91418966` Londrina – Nautico | same code map, every price matched |

**52 of 54 sampled code/price pairs matched exactly**; the two exceptions were
`266 = 1.00`, which the page renders as “manje 5.5 –” (no price). The live code
map is therefore the prematch map, proven per label, not assumed.

**Fix.** `config/bookmaker_markets.json` now declares Betole live rows for the
proven codes only (1x2 `1,2,3`; DC `7,8,9`; BTTS `272,273`; O/U 1.5
`242,21`; 2.5 `24,22`; 3.5 `25,219`; 4.5 `27,453`; 5.5 `223,266`). The capture
tool gained a live branch (`betole_live.json`, from the full-offer endpoint) and
`tests/test_wire_schemas_betole.py` pins the live scrape from it.

**Measured on the same probe, before → after:** `0` → **76 live matches**; market
families emitted: 1x2 75, double chance 76, BTTS 74, O/U 1.5 73, 2.5 76, 3.5 76,
4.5 67, 5.5 39.

## Mozzartbet — the HTTP list has no in-play events; the live list is a socket

The adapter's live path loads `/sr/kladjenje` and POSTs `/betting/matches` with
`date: "live"`. That answered **200 with 14 items, all in the future**
(`startTime` later that evening), so `_is_in_play` correctly filtered every one
and the book parsed to zero.

The site's own live page (`/sr/uzivo/sport/all`) does not call that endpoint for
live data. It opens a Socket.IO connection
(`wss://www.mozzartbet.ba/socket.io/?EIO=3&transport=websocket`) and receives
the live list as frames: `livematches` (per-event odds maps keyed by odd type
id, e.g. `{"1": 2.25, "2": 2.15, "3": 5.9}`), `sr_live_<sport>` (the market
catalogue behind those ids) and `streamPbpList` (scores). Six HTTP candidates
were tried in the page session (`/betting/matches` with `live: true`,
`/betting/live-matches`, `/betting/live/matches`, `/live/matches`,
`/betting/live`, `/betting/matches/live`); only `/betting/matches` returns JSON,
and none returns an in-play item.

So Mozzartbet live cannot be fixed inside the current HTTP path: it needs a
Socket.IO snapshot collector with its own captured frames, schema validation and
fail-closed rules. That is a transport change of its own scope, not a filter or
mapping fix. Until it exists, the adapter's live rows stay empty by design
(“can't read it” is reported as missing, never filled). The live destination
record likewise keeps Mozzartbet on `/sr/uzivo`.

## Where this leaves the scan

- Betole live is priced again (0 → 76 matches); its destination still needs the
  live-feed id question settled by SR9-2 (the route is `#/match` on WWIN, not
  Betole; Betole live stays copy-only until the score guard allows live legs).
- Mozzartbet live remains absent from every live scan until the socket
  collector is built.
